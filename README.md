SECTION 1: CTF OVERVIEW & RULES OF ENGAGEMENT
Challenge Scenario
Your Security Operations Center (SOC) SIEM has raised alerts regarding anomalous network traffic and DNS queries generated by multiple hosts. As a Tier-1 SOC Analyst, you are assigned a specific target domain, public IP, and an internal private subnet segment to investigate. Your goal is to conduct DNS reconnaissance, verify infrastructure records, trace reverse DNS mappings, evaluate IP reputation, and perform authorized port validation.
Required Investigation Tools & Commands
Utilize both native Linux CLI utilities and web-based OSINT threat intelligence tools:
1. Linux CLI Utilities:
○ DNS Reconnaissance: dig (A, AAAA, MX, NS, CNAME, PTR, +short, +trace), nslookup, host
○ Host & System Context: hostname, ip a, ip r
○ Port & Exposure Validation: nmap (-sS, -sV, -Pn, -p), nc -zv
2. Web OSINT Threat Intelligence Portals:
○ Reputation & Threat Scoring: VirusTotal - https://www.virustotal.com AbuseIPDB - https://www.abuseipdb.com/, https://www.ip2location.com/
○ Geolocation & ASN Lookup: IPLocation - https://www.iplocation.net/ Hurricane Electric BGP/DNS - https://bgp.he.net/, https://dnschecker.org/
Required Report Structure
Submit a report containing:
1. Executive Summary: Target assignment, high-level findings, and risk assessment score.

Just finished a SOC analyst CTF on DNS reconnaissance and network investigations, and it taught me something simple but important: an alert on an IP doesn’t mean the IP is malicious.

The scenario: investigate isc.org and the public IP 204.152.184.88 like a Tier-1 analyst.

What I did:

🔹 DNS recon: Used dig, nslookup and host to pull A, AAAA, MX and NS records. isc.org has 4 IPv4 and 4 IPv6 addresses, 2 mail servers and 5 name servers. I also found that www.isc.org sits behind a CDN (Fastly, 199.232.58.217), so the domain and the investigated IP aren’t necessarily the same web service.
🔹 Reverse lookup: The PTR query returned SERVFAIL, so I recorded “no result” instead of guessing.
🔹 Ownership and reputation: Checked ASN, geolocation, VirusTotal and AbuseIPDB. The IP belongs to ISC’s network (AS1280), and nothing pointed to malicious activity.
🔹 Exposure: An Nmap scan showed only ports 80 and 443 open, with everything else filtered. That’s normal for a public web service.

Result: Low risk. The better next step is to find out why the internal host contacted that IP, not to block it.
